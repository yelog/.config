# Astra → Luna 自动开发工作流

## 安装位置

- 插件：`~/.config/opencode-v2/plugins/task-workflow/index.ts`
- 启用配置：`~/.config/opencode-v2/opencode.json` 的 `plugins`
- 模型：Astra = `xrouter/gpt-6-astra`，Luna = `xrouter/gpt-5.6-luna`
- 分工：仅 analyze/plan（含这两个阶段内的纠偏）使用 Astra；命名、实施、收尾审查、后期纠偏、提交合并均使用 Luna。已有任务的 reviewPending 不改变该分工，恢复审查也使用 Luna。
- 当前适配：OpenCode V2.0.3

这是 opencode2 的全局插件，可以在不同 Git 项目中使用。新任务默认集中放在主 checkout 旁的 `<仓库名>-worktree/<任务名称>`，例如 `../my-api-worktree/add-cache`、`../lazydb-worktree/add-cache`。仓库名取自 Git 主 checkout，即使从已有 worktree 启动，也使用同一个默认父目录。

## 系统通知

插件关闭了 OpenCode 内置的逐轮 `Session done` 系统通知（`~/.config/opencode-v2/cli.json` 中的 `-opencode.notifications`）。原因是一个 `/task` 由多个 `session.prompt` 阶段组成，内置通知无法识别这些阶段属于同一个任务，会在分析、计划、实施等中间阶段分别弹窗。

现在由工作流 TUI 插件按任务状态发送通知：只有状态变为 `done`（完成、合并和清理完成）或 `blocked`（错误、外部输入、用户中断等终止）时，且终态发生变化，才发送一次通知。中间阶段、`running`、`cleaning`、收尾审查和普通阶段成功都不会通知。通知仅在终端失焦时发送，声音保持关闭；进度条仍实时更新。

这是全局 CLI 行为：关闭了所有普通会话的内置通知，但普通会话不会收到工作流终态通知，因为它们没有 `/task` 状态。若想恢复 OpenCode 原有逐轮通知，移除 `-opencode.notifications`，但会重新出现 `/task` 中间阶段弹窗。

## 项目级配置（可选）

在启动 checkout 根目录创建 `.opencode/task-workflow.json`（严格 JSON，不含注释）：

```json
{
  "prefix": "my-api",
  "parent": "../my-api-worktree",
  "planDirectory": "docs/plans",
  "models": {
    "astra": { "providerID": "xrouter", "id": "gpt-6-astra" },
    "luna": { "providerID": "xrouter", "id": "gpt-5.6-luna" }
  }
}
```

所有字段均可省略。prefix 默认主 checkout 目录名，仅用于构造默认父目录 `<prefix>-worktree`；任务子目录不再重复此前缀。parent 默认主 checkout 旁的 `<prefix>-worktree`，显式设置时覆盖默认父目录；相对路径从启动 checkout 根目录解析，也支持绝对路径。planDirectory 默认 `docs/plans`，必须是仓库内相对路径。模型可以只覆盖一个角色，但该角色需要完整 providerID 和 id。astra/luna 是阶段角色名称，允许替换成其他可用模型。

配置及目录布局只在 `/task` 启动时读取，随后保存到任务状态。修改项目配置不会改变已有任务的模型、目录和计划路径；旧版配置快照继续使用 `<prefix>-<任务名称>` 布局，没有配置快照的旧任务仍按原 lazydb 前缀恢复。现有 worktree 不搬迁。已有项目若显式设置 parent，新任务仍尊重该父目录，但子目录改为任务名称。

从已有 worktree 启动时，以该 checkout 为起点，并合并回它启动时的分支；不会自动切换到主 checkout。请从你希望最终接收合并的 checkout 启动。项目仍需要 Git、可用的模型及 writing-plans/git-commit Skills。非 Git 目录不支持。

## 开始使用

1. 退出并重新启动 opencode2，让新进程加载插件。
2. 在 `/Users/yelog/workspace/tui/lazydb` 打开一个新会话。
3. 检查主工作空间当前分支：它就是最终合并目标，不会强制切到 main。
4. 输入：

```text
/task 优化 Redis 上下文帮助
```

命令后面的全部文本都是需求，无需提供任务名称。Astra 完成计划后，Luna 根据会话上下文、需求和完整计划生成英文名称。插件检查本地分支、目录（包括符号链接）及 Git worktree 登记；重名时自动尝试 `-2`、`-3` 等后缀，并通过独占创建目录和 Git 分支创建再次防止并发冲突。一个会话承载一个任务；新任务使用新会话。

插件自动执行：

| 阶段 | 模型 | 行为 |
| --- | --- | --- |
| analyze | Astra | 分析现有实现、根因、方案取舍，写 analysis.md |
| plan | Astra | 调用 writing-plans，写完整 plan.md |
| implement | Luna | 创建 worktree、移动会话、逐项实施及复核、写 implementation.md |
| integrate | Luna | 验证、调用 git-commit、提交、合并、写 integration.md |

例如 Luna 生成 `redis-context-help`，会创建分支 `task/redis-context-help`，目录 `/Users/yelog/workspace/tui/lazydb-worktree/redis-context-help`；若重名则使用可用后缀。创建 worktree 前从原工作空间当前 HEAD 确定基线，包含用户在规划后提交的修改；启动时旧基线保留在 initialBase。已经存在的任务 worktree 不自动重建或变基。实际名称会显示在会话和 `/task-status` 中。

### 主工作空间有未提交修改

允许直接 `/task <需求>`。分析、计划阶段只读业务文件，产物保存在 Git common directory 的任务目录，不要求整个工作区干净。

计划阶段同时生成 `change-scope.json`，例如 `{"files":["src/app.rs","tests/input.rs"]}`。包含预计新增、修改、删除、重命名两端及计划依赖的未提交文件；仅读取的参考文件不在其中。允许具体目录，不允许模糊通配符。

实施前将清单与主工作区已暂存、未暂存、未跟踪文件比较（重命名检查两端），无重叠时正常创建 worktree；有重叠则保留分析和计划，暂停并列出具体路径。用户只需提交重叠文件，再 `/task-resume`，不会重复分析/计划。无关改动不复制到 worktree，不自动 stash、暂存、提交或覆盖。

每次实施续做还会检查已产生的实际修改；进入集成前按实际差异再次检查。模型被要求在扩大修改范围和真正执行 merge 前再次检查，Git 合并本身保留覆盖冲突保护。范围清单的完整性仍由模型负责，不是所有文件写入的强制拦截器。

最近的检查详情在 `workspace-check.json`。旧任务没有清单时：干净工作区直接继续，有本地修改则由 Luna 从现有计划提取清单；已有 worktree 保持其原基线。新分支基线更新后，Luna 应只核对受新提交影响的计划项。

### 计划文档的归属与提交

分析、计划阶段在主工作空间运行，而 `writing-plans` 技能默认把计划写到仓库的 `docs/plans/YYYY-MM-DD-<feature>-implementation.md`。如果放着不管，这些文件会以未跟踪状态残留在主工作空间。

插件在实施阶段会处理它们：

- `/task` 启动时记录计划目录下已有的未跟踪文件作为基线。
- 实施阶段把本次任务期间新出现的计划文档**移动**进新 worktree 的同一相对路径，并删除主工作空间副本。
- 该文档随后随任务一起提交、合并，因此最终以已跟踪文件出现在主工作空间，而不是未提交残留。
- 主工作空间副本与 worktree 中同名文件内容不同时，保留主工作空间副本并提示，不覆盖任何一方。
- 若计划阶段没有生成仓库文档，插件回退为把任务目录的 `plan.md` 复制成 `docs/plans/<task-name>.md`。

基线机制保证不会误移动其他任务或用户自己新增的文档；只有本任务运行期间新出现的计划文档才会被接管。因此同一个草稿不会产生两份已跟踪文档：有仓库文档时使用它，没有时才回退。

旧任务没有基线（无法判断哪些文档是它产生的），不会自动迁移。若历史任务留下未提交的计划文档，请按内容确认归属后手动处理：内容已存在于 `docs/plans/` 其他文件时可直接删除副本；内容未提交时可移入对应 worktree 随任务提交。

合并和验证通过后，会话先返回原工作空间，插件再执行 `git worktree remove` 和 `git branch -d`，删除本任务的 worktree 及分支。不会自动 push。公共父目录与 Git common directory 下的任务报告保留。

清理会同时删除 worktree 和分支。分支删除带三重校验：分支尖端必须等于集成时记录的已审查提交、该提交必须已包含在目标分支、且分支确实存在；任何一项不满足都会保留分支并说明原因，不使用 `-D` 强制删除。删除分支是无损的，因为该提交已进入目标分支。

清理前还会核对目标分支、任务 worktree 的分支与 HEAD，以及未提交/未跟踪文件。不会使用强制删除；正常 Git worktree 删除也会移除该目录内被忽略的构建产物。若清理失败，任务停在清理阶段，处理原因后 `/task-resume` 只重试清理，不再调用模型重复实施或合并。

### 清理历史遗留

早期版本完成的任务可能只删除了 worktree，留下已合并的 `task/*` 分支。使用维护命令清理：

```text
/task-cleanup          # 只列出可清理项与跳过原因
/task-cleanup remove   # 实际删除
```

它扫描本仓库 `.git/opencode-tasks` 下的任务记录，只有在「分支尖端等于已审查提交、该提交已进入目标分支、worktree 干净、无未提交/未跟踪文件」时才会删除，否则逐条报告跳过原因。因此进行中的任务、未合并分支和带未提交改动的工作树都不会被误删。命令幂等，可重复运行；已清理的任务不再列出。

## 查看进度

### 输入框上方常驻阶段条

插件自带 `./tui` 入口，随服务端插件自动加载。重启 opencode2 后，有任务的会话会在输入框上方显示两行：

```text
✓ 分析 → ✓ 计划 → ● 实施 → ○ 集成 → ○ 清理
redis-value-editing · gpt-5.6-luna · 收尾审查 · 第 3 轮 · 下一步…
```

✓ 表示阶段已完成，● 表示当前执行阶段，○ 表示尚未进入，! 表示当前阶段暂停。阶段颜色使用语义化主题色：已完成为绿色；分析为青色、计划为紫色、实施为蓝色、集成为橙色、清理为绿色；当前阶段加粗，未开始阶段使用低亮度灰色，暂停使用橙色。这样即使终端不支持颜色，符号仍保留原有含义。

第二行显示任务名、实际配置的阶段模型、状态、轮次及下一步/错误摘要：任务名使用正常文本，模型、分隔符和辅助信息使用弱化文本；状态使用与状态一致的颜色（完成绿、运行蓝、审查紫、暂停/等待橙）。长文本受终端宽度限制，详细内容仍使用 `/task-status`。

没有任务的会话不占空间。清理也显示为独立阶段；全部完成后五项均勾选。仅展示阶段进度，不估算完成百分比。TUI 根据 OpenCode 权限/表单缓存显示等待授权或输入；服务器进程已退出的 running 记录显示为待恢复，不假装持续执行。

服务端通过只读 RPC 提供状态并在保存后发送事件，TUI 每三秒补读一次以恢复丢失事件/断线状态。此过程不调用模型、不自动恢复任务。切换会话按 sessionID 读取，worktree 移动后按会话当前目录访问。state.json 使用临时文件加原子替换写入，避免 UI 读到半写入内容。

关键文件：`rpc.ts`（协议/展示摘要）、`tui.tsx`（输入框上方组件）、`index.ts`（服务端状态和事件）。已使用真实 V2 TUI + 伪终端捕获验证五阶段及完成状态实际渲染。

```text
/task-status
```

显示当前阶段、状态、分支、worktree、报告目录和阻塞原因。模型和工具的实际执行过程仍显示在当前会话中。

## 暂停与继续

### 自动续做与纠偏

模型回执支持 completed（整个阶段完成）、progress（有进展，自动续做）、blocked（声明外部阻塞）。缺少或格式错误的回执先自动补做，不立即要求用户 resume。新协议要求复杂任务按端到端可验收单元推进，普通实现取舍自行决定。

实施阶段连续两轮工作区内容无变化、连续六轮未完成、模型声明 blocked，或下一步涉及人工交互验收/PTY 时，进入 **Luna 收尾审查**。同一会话继续使用 Luna，通过实际工具读取源码、diff 和验证记录，区分真正功能缺口与补充验收。其他阶段仍使用短文本纠偏（最多两次），模型跟随当前阶段：分析/计划用 Astra，后期用 Luna。每次人工恢复最多 40 轮、最多三次收尾审查，避免无限空转。源码指纹包含 HEAD、已跟踪 diff 和未跟踪文件内容（排除默认 docs/plans）；这是停滞启发式检测，不等于功能验收。

收尾审查有三种结果：
- 完成：必须提供逐项需求证据、空 remainingRequired，以及 deferredChecks（可为空）。只能延后非强制的补充检查，并写明原因；实际功能缺口或用户/项目强制验证不能跳过。结构校验通过后才进入集成，证据真实性仍由审查模型负责。
- 继续：提供非空 remainingRequired 与具体修复步骤，由 Luna 继续修复并再次审查。
- 必需外部输入：明确问题后暂停，不反复假装 progress。

审查记录保存在 `completion-review-N.md`，通过后的机器可读结论为 `completion-decision.json`。集成阶段读取结论，复用仍适用的验证结果，不重新开启已判定为补充性质的环境受限手测，并在最终交付中列明限制。不会把未执行手测标成通过。

当前回执路径/token 在每轮开始前持久化到 state.json 的 activeReceipt，`/task-status` 显示它、轮次、收尾审查次数及下一步。旧 token 无效，模型只写本轮回执，不能覆盖旧回执；checkpoint.json 由插件维护。旧任务恢复时，重置预算前先识别已有停滞/人工验收信号，优先进入审查。

已记录的 429/5xx 等临时模型错误会退避自动重试，最多三次。用户中断仍保持停止。需要外部输入、持续无进展、非临时错误或达到预算时才交还用户。原有任务 resume 后也采用新协议。

`checkpoint.json` 保存当前轮进度、下一步与验证摘要；`correction-<stage>-N.txt` 保存当前阶段模型的纠偏建议。`validation.md` 由执行模型维护命令、结果及代码/环境依据，要求同一代码和环境复用已成功检查、相关变化后才重跑。这是模型执行规则，尚不是由插件代理 shell 的强制测试缓存。

当前仍使用同一会话与四阶段结构；不会自动创建新执行会话或合并分析/计划阶段。

使用 OpenCode 当前配置的停止操作中断模型，流程会停在当前阶段。普通未完成会自动续做，真实外部阻塞或自动恢复预算耗尽时暂停。

处理问题或补充需求后，在原会话输入：

```text
/task-resume
```

恢复会重新执行当前未完成阶段，已完成阶段不会从头运行。实施阶段会检查已有 worktree 并继续使用它。若关闭或重启 OpenCode，也应重新打开原会话后运行此命令。

任务仍在执行时 resume 会拒绝重复启动。不要在多个 opencode2 进程中同时恢复同一个会话。

## 状态和报告

数据保存在 Git common directory 下：

```text
<git-common-dir>/opencode-tasks/<session-id>/
  state.json
  analysis.md
  plan.md
  implementation.md
  integration.md
  <stage>-<token>.json
```

正常主工作空间中就是 `.git/opencode-tasks/<session-id>/`。使用 `/task-status` 获取本任务准确路径。

阶段推进要求模型写入带本轮 token 的完成回执、对应报告非空，且会话未失败或中断。合并阶段额外检查任务 HEAD 已进入目标分支及任务 worktree 干净。验证结果内容由模型执行并报告，插件不会独立重跑任意项目的测试命令。

## 常见情况

- **自动命名**：Luna 使用独立文本请求，输入需求、分析及完整计划，避免会话内的执行指令干扰命名。接受纯 slug、JSON 和代码块等包装；无效结果自动重试，最多三次。原始返回保存为 `naming-1.txt` 等诊断文件。
- **branch/tree 为空**：分析和计划阶段这是正常状态，实施前才分配名称。不要让模型手动编辑 `state.json`。将状态改成 `running` 不会启动执行，必须使用 `/task-resume`。
- **手动创建过本任务 worktree**：恢复时插件核对已记录路径、分支、Git worktree 登记、仓库和基线，通过后补齐名称与创建标记，继续使用；不匹配则停止，不盲目接管。

- **找不到命令**：退出并重新启动 opencode2，确认使用的是 V2 的启动脚本。
- **主工作空间有未提交改动**：允许先分析和计划；实施前仅在计划文件与本地修改重叠时暂停。提交提示列出的重叠文件后 `/task-resume`；无关修改可继续保留。
- **同名分支或目录存在**：插件自动选择可用后缀，不会复用冲突的 worktree。已有任务应在原会话中 resume；已成功创建并记录的 worktree 会继续复用。旧版手动命名任务仍可恢复。
- **权限询问**：按 OpenCode 提示允许任务需要的操作，尤其是新 worktree 和 `.git/opencode-tasks` 的文件访问。插件没有更改全局工具权限。
- **分支没有随任务删除**：确认任务已走到清理阶段（状态 `done`）。若分支尖端有未合并到目标分支的新提交，插件会保留它并说明原因。历史遗留可用 `/task-cleanup` 处理。
- **需要补充需求**：先在原会话说明补充内容，处理完后 resume。
- **合并冲突或验证失败**：查看当前会话和报告，处理后 resume。插件不会把“模型停止输出”当作成功。
- **要修改模型**：在项目 `.opencode/task-workflow.json` 中覆盖 models，对之后启动的任务生效。全局默认值仍位于 `index.ts` 顶部 models。
- **禁用**：从 V2 配置的 `plugins` 中移除本插件路径，重启 opencode2。
